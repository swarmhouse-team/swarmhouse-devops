# Резервное копирование PostgreSQL

В репозитории два скрипта:

- `scripts/backup-postgres.sh` — дамп одной базы и глобальных объектов;
- `scripts/restore-postgres-test.sh` — проверка этого дампа в новой базе.

Оба файла уже хранятся в Git с правом исполнения. Отдельный `chmod +x` не нужен. Расписания, шифрования и копии вне этого VPS в репозитории нет. Каталог бэкапов на том же диске не спасает данные, если пропадёт VPS.

Redis этими скриптами не архивируется. В `conf/redis/redis.conf` включены AOF и `appendfsync everysec`, RDB-снимки выключены (`save ""`). Это устойчивость контейнера Redis, а не бэкап.

Зависимости скриптов на хосте: Bash, Docker CLI, `flock`, `sha256sum`, `find`, `date`, `mkdir`. Скрипты вызывают `pg_dump`, `pg_dumpall`, `pg_restore` и `createdb` внутри контейнера `postgres`, а не с хоста.

## Что сохраняет backup-postgres.sh

Имя базы скрипт читает из `POSTGRES_DB` внутри контейнера `postgres`, не из своей оболочки. Пользователь дампа — `POSTGRES_USER` того же контейнера.

В каталог попадает:

- один файл `<POSTGRES_DB>.dump` — `pg_dump -Fc` только этой базы;
- `globals.sql` — `pg_dumpall --globals-only` (роли и табличные пространства, без содержимого баз);
- `SHA256SUMS` по файлам каталога.

Каталог данных PostgreSQL, WAL и остальные базы не копируются. Пароль в архив не записывается: клиент внутри контейнера использует уже заданное окружение.

Каталог бэкапа: `<корень репозитория>/data/backup/<ГГГГ-ММ-ДД_ЧЧ-ММ-СС>`. Путь считается от расположения скрипта, поэтому текущий каталог оболочки не важен. `data/backup` указан в `.gitignore`.

Незавершённый каталог создаётся как `.tmp-<штамп>` и при ошибке удаляется. Готовое имя появляется только после проверки `pg_restore --list`, непустого дампа и записи сумм. Каталог `data/backup` создаётся с правами `700`, umask скрипта `077`.

Одновременно запускается один экземпляр: блокировка `scripts/.backup-postgres.lock`. Если блокировка занята, скрипт выходит с кодом 1.

После успеха скрипт оставляет пять самых новых каталогов, чьи имена начинаются с `20`, и остальные такие каталоги удаляет. Это единственная ротация. Чужие файлы в `data/backup`, не подходящие под этот шаблон, он не трогает.

Запуск из корня репозитория:

```bash
./scripts/backup-postgres.sh
```

Контейнер `postgres` должен быть запущен. Иначе скрипт завершится с ошибкой и архив не создаст.

## Проверка восстановления

`restore-postgres-test.sh` не восстанавливает исходную базу и не применяет `globals.sql`. Он проверяет контрольные суммы, создаёт новую базу и загружает в неё единственный `.dump`.

```bash
./scripts/restore-postgres-test.sh data/backup/<ГГГГ-ММ-ДД_ЧЧ-ММ-СС>
```

Второй аргумент необязателен. По умолчанию имя `restore_test_<ГГГГММДД_ЧЧММСС>`. Своё имя должно начинаться с `restore_test_`, содержать только `a-z`, `0-9` и `_` и быть не длиннее 63 символов. Иначе скрипт откажется работать.

Контейнер по умолчанию `postgres`. Другой контейнер задаётся переменной `POSTGRES_CONTAINER`.

Скрипт требует каталог, файл `SHA256SUMS` и ровно один непустой `*.dump`. Проверка сумм: `sha256sum --strict -c SHA256SUMS`. База создаётся через `createdb` от `POSTGRES_USER`, `--template=template0`, служебная база `postgres`. Загрузка: `pg_restore -d <новая база> --single-transaction`.

Исходная база не открывается на запись. Если имя уже занято, `createdb` завершается с ошибкой и `pg_restore` не запускается.

После успешного окончания тестовая база остаётся. Скрипт её не удаляет. После ошибки `pg_restore` база тоже остаётся: сообщение скрипта прямо говорит, что она не удалена. Неудачный `.tmp` бэкапа это не затрагивает.

Пока тестовая база не нужна, её удаляют отдельной командой. Это уже разрушающее действие, его нет в скрипте:

```bash
docker exec postgres sh -ec 'dropdb -U "$POSTGRES_USER" --maintenance-db=postgres "$1"' sh restore_test_<имя>
```

Перед `dropdb` имя стоит ещё раз прочитать в выводе скрипта. Команда удаляет указанную базу целиком.

Playbook после успешного `backup-postgres.sh` вызывает этот скрипт, сверяет `current_database()` с именем `restore_test_*` и удаляет только эту базу. Рабочая база командой восстановления не открывается. Каталог бэкапа остаётся на том же VPS. Внешней копии нет. Успешный прогон на конкретном сервере этой документацией не подтверждается, пока playbook там не выполнен.
